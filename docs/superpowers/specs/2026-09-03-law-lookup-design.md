# 小六法即時查詢工具 — 設計文件

- 日期:2026-09-03
- 狀態:設計完成,待實作
- 目標讀者:實作者(人或 agent)

## 1. 背景與目標

上法律課程時需要頻繁查閱法條。紙本小六法笨重,全國法規資料庫的網頁搜尋每次查詢都要一輪頁面往返,節奏跟不上課堂。

本工具要解決的是**查閱速度**:

1. 打字的同時即時出結果,不需按 Enter、不需等待
2. 用最短的鍵入抵達條文——`民184` 三鍵即到民法第 184 條
3. 命中之後能從該條**自由往上下捲動**閱讀前後條文,像翻紙本一樣
4. 教室網路不穩時仍完全可用

### 成功標準

- 從按下第一個鍵到看到結果 < 50 ms(實測目標,見 §11)
- 完全離線可用
- 核心搜尋邏輯不綁定 UI 框架,日後新增手機版 UI 不需改動核心

## 2. 非目標

以下項目經評估後明確排除,不在本版範圍:

- **釋字 / 憲判字關聯**:開放資料無此層關聯,需另爬司法院並自行對接,工程量與維護成本不成比例
- **立法理由**:開放資料完全沒有,來源散在立法院公報與各部會網站,格式不一,無法可靠自動化
- **跨裝置同步**:離線優先加多裝置即時同步是獨立難題。以匯出/匯入 JSON 替代
- **模糊搜尋 / 拼字校正**:中文打錯字產生的是完全不同的字,edit distance 在中文上不具意義
- **判決書、行政函釋、命令層級法規**:本版只收「中央法律」

### 3.3 解析時必須處理的六個陷阱

這六項都是實際踩過的,不是臆測:

1. **`編章節` 是扁平的兄弟節點**,不是巢狀容器。它依文件順序穿插在 `條文` 之間。層級靠前導空白編碼,每階 3 格:`第 一 編`(0 格)、`   第 一 章`(3 格)、`      第 一 節`(6 格)、`         第 一 款`(9 格)。因此 `level = 前導空白數 / 3`。

2. **條號需正規化**。格式為 `第 184 條` 或 `第 184-1 條`,全庫有 1,359 種帶橫線的條號。必須解析成 `{main: 184, sub: 1}`,否則字串排序會把 `184-1` 排到 `185` 之後,而正確順序是 `184 < 184-1 < 185`。

3. **口語名稱與正式名稱不同**。「刑法」在資料庫中的正式名稱是「中華民國刑法」。這使別名表成為必要基礎設施,而非加分功能。

4. **法規名稱可能帶括號後綴**。「總統副總統選舉罷免法」的實際名稱是「總統副總統選舉罷免法（新 84.08.09 制定）」;「最低工資法（112.12.27制定）」同理。因此:以 PCode 為唯一 key,顯示一律用清單自訂的 `abbr`。

5. **廢止過濾必須在名稱比對之前**。322 部帶 `廢止註記` = `廢`,其中包含舊版總統副總統選舉罷免法。若先比對名稱再濾,會抓到已廢止版本。

6. **PCode 需從 `法規網址` 以 regex 取出**:`/pcode=(\w+)/i`。XML 中沒有獨立的 PCode 欄位。

### 3.4 建置流程

```
下載 FalV.zip → 解壓 → 濾除廢止 → 依 laws.yaml 挑 100 部
  → 解析 blocks → 驗證 → 輸出 public/corpus.json + manifest
```

**fail-fast 驗證**(任一項失敗即中止建置並報告):

- `laws.yaml` 中的每個 PCode 都必須在來源中存在且未廢止
- 別名不得重複,亦不得與任何 `abbr` 衝突
- 每部法至少有 1 條條文
- 每個條號都能被條號 regex 解析

安靜產出一份缺法的 bundle 比建置失敗危險得多——使用者會以為自己查過了。

## 4. 資料模型

```ts
type Division = { t: 'd'; level: 0 | 1 | 2 | 3; label: string };

type Article = {
  t: 'a';
  no: string;      // 正規化條號,如 "184" 或 "184-1"
  main: number;    // 184
  sub: number;     // 1;無「之」號時為 0
  label: string;   // 顯示用原文,如 "第 184 條"
  text: string;    // 條文內容,各項以 \n 分隔
};

type Block = Division | Article;

type Law = {
  pcode: string;      // "B0000001"
  name: string;       // 來源原始名稱
  abbr: string;       // 顯示名稱,取自 laws.yaml
  aliases: string[];
  group: string;      // 分類
  updated: string;    // "20260817"
  history: string;    // 沿革內容
  preamble?: string;
  blocks: Block[];    // 依原始文件順序
};

type Corpus = {
  sourceUpdatedAt: string;  // 來源 UpdateDate
  builtAt: string;
  laws: Law[];
};
```

**單一 bundle,不拆檔**。離線需要全載、全文搜尋也需要全載,拆成 100 個檔只會換來 100 次請求。月更一次的資料整包替換沒有任何損失。

## 5. 查詢語法與解析

### 5.1 語法

單一輸入框,不需切換模式:

| 輸入 | 意義 |
|---|---|
| `184` | 在目前開啟的法規內跳至第 184 條(未開啟法規時見 §5.4) |
| `民184` / `民法184` / `民法 184` | 民法第 184 條 |
| `民184-1` / `民法184之1` / `民§184-1` | 民法第 184 條之 1 |
| `過失` | 全域關鍵字搜尋 |
| `民法 過失` | 限定民法內搜尋「過失」 |
| `過失 傷害` | 兩關鍵字皆須出現(AND) |

### 5.2 解析流程

1. **正規化**:全形數字轉半形;剝除 `§`、`第`、`條`;`之` 轉 `-`;壓縮空白
2. **剝離法規前綴**:對別名表做**最長匹配**
3. **判定意圖**:剩餘字串符合 `^\d+(-\d+)?$` → 條號查詢;否則 → 關鍵字查詢,範圍為剝出的法規,未剝出則為全域

### 5.4 純數字查詢的兩種情境

`184` 這類純數字查詢的行為取決於右欄目前是否已開啟法規:

- **已開啟法規**:在該法規內跳至第 184 條。這是課堂上最常見的情境——正在讀民法,直接打 `184` 即可。
- **未開啟任何法規**:列出六法核心(憲法、民法、民事訴訟法、刑法、刑事訴訟法、行政程序法)中該條號存在的候選,依 §6.3 的分類順序排列,讓使用者以 `↑` `↓` 選擇。

不採用「猜測最近一次瀏覽的法規」的做法——猜錯時使用者會看到條號正確但法規錯誤的條文,而這種錯誤在課堂上難以察覺,後果比多按一次方向鍵嚴重得多。

### 5.3 最長匹配是必要的

`民` 是 `民訴` 的前綴。若採最短匹配,`民訴244` 會被解析成「民法」加殘餘字串 `訴244`,查詢失敗。同類衝突尚有 `刑` / `刑訴`、`行` 系列。實作必須依別名長度由長到短嘗試。

## 6. 搜尋引擎

### 6.1 演算法:brute-force 子字串比對

對全部 11,942 條條文逐一 `indexOf`,多 term 取 AND,同時收集所有命中位置供高亮使用。

不建索引、不使用搜尋函式庫。理由見 §11 實測:最壞情況 7.5 ms,而 MiniSearch 等方案需付出 11.7 MB 索引與約 1 秒冷啟動,只為換取 0.8 ms 的查詢加速——在 100 ms 的人類感知門檻之下,這個交換沒有意義。

### 6.2 執行環境:主執行緒,無 Worker,無 debounce

最壞情況仍在單一影格(16.7 ms)內完成。移入 Web Worker 反而要付 `postMessage` 序列化成本,更慢且更複雜。每次 keystroke 同步搜尋即可。

### 6.3 排序與呈現:依法規分組

結果**依法規分組**,而非扁平的相關性排序。這較貼近法律人的心智模型——使用者想知道「民法裡有哪幾條」,而不是「全部命中的第 7 名」。

- 法規順序:`laws.yaml` 的分類順序
- 組內順序:命中次數多者優先,其次條號由小到大
- 條號查詢的結果永遠釘在最上方

**不做 BM25**。BM25 偏好短文件,與本場景需要的排序意圖不符;自訂規則更貼近需求。

**不截斷結果**。查法條時「不知道自己有沒有漏掉」是危險的。全部命中都保留,標題列顯示「共 N 條命中,分布於 M 部法規」。

### 6.4 零結果處理

不做「你是不是要找…」的猜測。改為指出造成零命中的 term:

> 「第三人保護」無命中,移除後有 23 條

這比模糊猜測實際得多,也誠實得多。

## 7. UI 與互動

### 7.1 版面

雙欄。左欄(約 340 px)為搜尋輸入與結果清單,右欄為連續閱讀區。

### 7.2 鍵盤操作

| 鍵 | 行為 |
|---|---|
| (任意字元) | 焦點預設永遠在搜尋框,開啟即可打字 |
| `↑` `↓` | 移動左欄選取(跳過分組標題),右欄同步跳至該條 |
| `Enter` | 焦點移至右欄,進入閱讀 |
| `Esc` | 清空查詢;查詢已空時焦點回搜尋框 |
| 滾輪 / `PageUp` `PageDown` | 右欄自由捲動 |
| `[` `]` | 跳至上一個 / 下一個編章節 |
| `Cmd+D` | 對目前條文加書籤 |

### 7.3 單向同步

左欄選取移動時右欄跟隨跳轉;**右欄自行捲動時左欄選取不變**。

這是刻意的設計。若做成雙向,使用者為了閱讀鄰近條文往下捲兩頁,左欄選取會一路跳動,干擾嚴重。

### 7.4 右欄閱讀區:全渲染,不做虛擬捲動

一次渲染目前法規的全部 blocks,以 `scrollIntoView({block:'center'})` 定位。

實測(見 §11)顯示最大的一部法(民法 1,439 條)全渲染只需 30 ms 即可互動。虛擬捲動在此不但沒有必要,還會帶來高度估算誤差與「跳轉後往上捲動抖動」的經典問題。全渲染另有兩個附帶好處:定位精確、瀏覽器原生 Ctrl+F 可用。

編章節標題以 `position: sticky` 釘在頂端,提供紙本書眉的功能——往下捲動時始終知道自己身處第幾編第幾章。

### 7.5 高亮

搜尋時一併收集的命中位置,供左欄摘要與右欄閱讀區共用。

## 8. 個人資料層

IndexedDB(以 `idb` 薄封裝),三個 store,key 一律為 `${pcode}:${no}`:

| Store | 結構 | 說明 |
|---|---|---|
| `history` | `{ts, query, pcode, no}` | 保留最近 200 筆,超出自動裁切 |
| `bookmarks` | `{pcode, no, ts}` | |
| `notes` | `{pcode, no, body, updatedAt, lawVersionAtWrite}` | `body` 為原始 Markdown |

### 8.1 修法偵測

筆記寫入時一併記錄該法當時的「最新異動日期」為 `lawVersionAtWrite`。載入時與目前 corpus 的日期比對,不同則在筆記上顯示:

> 此條所屬法規已於 2026-08-17 修正,你的筆記寫於修正前

不自動處理、不隱藏、不推測改了什麼。只告知需要重看。

### 8.2 入口與編輯

搜尋框為空時,左欄顯示「書籤」與「最近查詢」兩區。有筆記的條文在右欄條號旁顯示標記。筆記支援 **Markdown**,採「編輯 / 預覽」雙態:聚焦時是 textarea 顯示原始碼,失焦後渲染為 HTML,點擊即回到編輯。不做並排即時預覽——課堂筆記是寫完就看,並排會白白吃掉右欄寬度。

儲存 500 ms debounce,`body` 一律存**原始 Markdown 文字**,不存渲染後的 HTML。

渲染以 `marked` 解析,並**必須經 `DOMPurify` sanitize 後才插入 DOM**。雖然筆記出自使用者自己,但 §8.3 的匯入功能會接受外部 JSON 檔,未經 sanitize 的渲染路徑等於給匯入功能開了一個 XSS 缺口。

### 8.3 備份

匯出 / 匯入 JSON,為本版唯一的備份與跨裝置手段。

## 9. 專案結構

```
law/

    laws.yaml            # 100 部清單:pcode / abbr / aliases / group
    build.ts             # 下載 → 解析 → 驗證 → 產出 corpus.json
  src/
    core/                # 零框架依賴,手機版可完整複用
      types.ts

    store/
      db.ts              # IndexedDB
    ui/                  # 唯一綁定框架之處
      App.tsx
      SearchPane.tsx
      ReaderPane.tsx

```

技術堆疊:React + TypeScript + Vite,`vite-plugin-pwa`,`idb`,`marked` + `DOMPurify`(筆記渲染),Vitest。

`src/core/` 不得 import 任何 UI 框架。這是「日後擴充手機版」的具體保證,同時也是最容易測試的邊界。

## 10. 測試策略

採 TDD,重心壓在 `core/`。

| 模組 | 測試重點 |
|---|---|
| `articleNo` | `第 184-1 條` → `{main:184, sub:1}`;排序斷言 `184 < 184-1 < 185` |
| `alias` | `民訴244` 須解析為民事訴訟法(最長匹配);`民184之1`;`民§184-1`;全形數字 |
| `parseQuery` | §5.1 六種語法形態各一組 |
| `search` | 精確命中、多 term AND、零命中 term 的定位、分組排序 |
| `notes` | Markdown 渲染經過 sanitize:含 `<script>` 或 `onerror` 的筆記 body 渲染後不得留下可執行內容 |
| `build` | **對真實 corpus 斷言**:100 部全在;民法有 1,439 條;民法第 184 條開頭為「因故意或過失」;別名無重複 |

`build` 那組是最重要的。法規改版或來源格式變動是這個專案最可能安靜壞掉的地方,這組測試是唯一的防線。

UI 測試不追求覆蓋率,只測一條鍵盤流:輸入 → `↓` → `Enter` → 右欄定位正確。

## 11. 實測數據

以下數據為設計決策的依據,於 2026-09-03 量測。搜尋 benchmark 跑在 99 部 / 11,814 條 / 1,352,607 字的語料上(第 100 部總統副總統選舉罷免法為稍後補入,占比 1.6%,對結論無影響)。

### 11.1 搜尋:brute-force vs MiniSearch

| | brute-force `indexOf` | MiniSearch 7.2 + bigram tokenizer |
|---|---|---|
| 查詢平均 | 1.02 ms | 0.21 ms |
| 索引檔大小 | 0 | 11.7 MB(為語料的 2.2 倍) |
| 冷啟動 | 0 ms | `loadJSON` 1,063 ms(不預建則 `addAll` 2,746 ms) |
| 誤判率 | 0%(定義上精確) | 0%(實測) |

結論:MiniSearch 品質沒有問題,但成本結構完全不成比例。

### 11.2 brute-force 最壞情況

| 查詢 | 命中數 | 耗時 |
|---|---|---|
| `不當得利` | 12 | 3.45 ms |
| `公司 董事 監察人` | 86 | 1.25 ms |
| `之`(最壞情況) | 10,342 | 7.51 ms |
| 逐字輸入「損害賠償責任」(7 次搜尋累計) | — | 3.8 ms |

### 11.3 全渲染(民法 1,439 條,Chrome)

| 指標 | 實測 |
|---|---|
| DOM 節點 | 5,637 |
| `domInteractive` | 30 ms |

## 12. 離線與部署

`vite-plugin-pwa` precache app shell 與 `corpus.json`。

啟動時於背景比對遠端資料版本,有新版則提示「法規資料有更新,重新載入」。**不自動靜默更新**——使用者可能正在對照條文,腳下的資料不應無預警替換。

介面上固定顯示資料版本(如「資料版本 2026-08-21」)。查法條時,不知道自己看的是不是現行版本,比慢一點嚴重得多。

部署至 GitHub Pages。

## 13. 已知風險與未來擴充

### 風險

| 風險 | 影響 | 緩解 |
|---|---|---|
| 來源 XML 格式變動 | 建置產出錯誤資料 | §10 的 build 驗證測試 + fail-fast |
| 法規改名或廢止 | 該法從 bundle 中消失 | 以 PCode 為 key;建置時 PCode 不存在即失敗 |
| 別名表需人工維護 | 新增法規時可能衝突 | 建置時檢查衝突並中止 |

### 未來擴充(明確不在本版)

- 手機版 UI:新增消費 `src/core/` 的 UI,核心不需改動
- 擴大收錄至全庫 1,346 部:語料增至約 17 MB,brute-force 約 13 ms,架構不需改變
- 跨裝置同步:需引入後端或雲端儲存,屆時重新設計
